# บทที่ 4 การวิเคราะห์ระบบและการพัฒนาโปรแกรม

เอกสารฉบับนี้สรุปการวิเคราะห์ ออกแบบ พัฒนา และทดสอบระบบเฉพาะส่วนเว็บไซต์ของโครงการพอร์ทัลเอกสารจัดซื้อจัดจ้างจังหวัดขอนแก่น โดยอ้างอิงจากโค้ดที่พัฒนาอยู่จริงในระบบ ไม่รวมขอบเขตงาน OCR หรือการดึงข้อมูลจากแหล่งภายนอก

## 4.1 การวิเคราะห์ระบบ

### 4.1.1 ภาพรวมปัญหาและขอบเขตของระบบ

ระบบเว็บไซต์ถูกพัฒนาขึ้นเพื่อเป็นศูนย์กลางสำหรับค้นหาและติดตามประกาศจัดซื้อจัดจ้างของหน่วยงานในจังหวัดขอนแก่น ผู้ใช้งานสามารถค้นหาประกาศจากคำสำคัญ ชื่อหน่วยงาน ประเภทวิธีการจัดซื้อจัดจ้าง หมวดหมู่ และช่วงงบประมาณ พร้อมดูรายละเอียดของประกาศและไฟล์ PDF ที่แนบมาได้จากหน้าเว็บโดยตรง

ขอบเขตของระบบในส่วนเว็บไซต์ประกอบด้วย 3 กลุ่มผู้ใช้งานหลัก ได้แก่

1. ผู้เยี่ยมชมทั่วไป (Guest) สามารถค้นหา ดูรายการประกาศ ดูรายละเอียดประกาศ และเปิดเอกสาร PDF ที่เผยแพร่แล้วได้
2. ผู้ใช้ที่ลงทะเบียนและยืนยันอีเมลแล้ว (Registered User) ใช้งานความสามารถของ Guest ได้ทั้งหมด และเพิ่มความสามารถด้านการบันทึกการค้นหา ประวัติการค้นหา ประวัติการเข้าชมประกาศ แดชบอร์ดส่วนตัว และการแจ้งเตือน
3. ผู้ดูแลระบบ (Administrator) สามารถจัดการประกาศ จัดการผู้ใช้ และดูภาพรวมการใช้งานผ่านแดชบอร์ดผู้ดูแลระบบได้

ระบบนี้ใช้แนวคิด role-based access control โดยแบ่งสิทธิ์ด้วยค่า `role` ของผู้ใช้เป็น `registered` และ `admin` ส่วน Guest จะเป็นผู้ใช้งานที่ยังไม่เข้าสู่ระบบ จึงไม่ถูกเก็บเป็นบทบาทในฐานข้อมูล

### 4.1.2 รายการความต้องการของระบบ

#### 1) ความต้องการเชิงหน้าที่

1. ระบบต้องเปิดให้ผู้เยี่ยมชมค้นหาประกาศจัดซื้อจัดจ้างได้โดยไม่ต้องเข้าสู่ระบบ
2. ระบบต้องแสดงรายละเอียดของประกาศที่เผยแพร่แล้ว พร้อมไฟล์แนบ PDF ที่สัมพันธ์กับประกาศนั้น
3. ระบบต้องรองรับการกรองประกาศด้วยคำค้น หน่วยงาน วิธีจัดซื้อจัดจ้าง หมวดหมู่ และช่วงงบประมาณ
4. ระบบต้องเก็บประวัติการค้นหาเฉพาะผู้ใช้ที่เข้าสู่ระบบและยืนยันอีเมลแล้ว
5. ระบบต้องเก็บประวัติการเข้าชมประกาศเฉพาะผู้ใช้ที่เข้าสู่ระบบและยืนยันอีเมลแล้ว
6. ระบบต้องให้ผู้ใช้บันทึกชุดเงื่อนไขการค้นหาเป็นรายการค้นหาที่บันทึกไว้ (Saved Search) ได้
7. ระบบต้องให้ผู้ใช้เปิดหรือปิดการแจ้งเตือนของแต่ละ Saved Search ได้
8. ระบบต้องรองรับการแจ้งเตือนผ่านหน้าเว็บไซต์และอีเมลตามค่าที่ผู้ใช้กำหนด
9. ระบบต้องประเมินประกาศใหม่กับ Saved Search แบบ background job เมื่อมีการเผยแพร่ประกาศ
10. ระบบต้องให้ผู้ดูแลระบบเพิ่ม แก้ไข ซ่อน เผยแพร่ และลบประกาศได้
11. ระบบต้องให้ผู้ดูแลระบบเปลี่ยนสิทธิ์ผู้ใช้และลบผู้ใช้ได้ โดยต้องป้องกันการลบหรือลดสิทธิ์ผู้ดูแลระบบคนสุดท้าย
12. ระบบต้องบังคับสิทธิ์การเข้าถึงจากฝั่งเซิร์ฟเวอร์ ไม่พึ่งการซ่อนเมนูในฝั่ง frontend เพียงอย่างเดียว
13. ระบบต้องรองรับการยืนยันตัวตนด้วยอีเมล/รหัสผ่าน การยืนยันอีเมล การลืมรหัสผ่าน และ two-factor authentication

#### 2) ความต้องการเชิงไม่ใช่หน้าที่

1. ระบบต้องรองรับการแบ่งส่วน presentation layer และ backend logic อย่างชัดเจน
2. ระบบต้องพัฒนาให้สามารถทดสอบอัตโนมัติได้ทั้งระดับ feature test และ browser test
3. ระบบต้องมีการจัดคิวงานแจ้งเตือนเพื่อไม่ให้การเผยแพร่ประกาศช้าเกินจำเป็น
4. ระบบต้องมีโครงสร้างที่ขยายต่อได้ เช่น การเพิ่มฟิลด์ประกาศหรือเพิ่มช่องทางแจ้งเตือนในอนาคต
5. ระบบต้องมีการป้องกันการเข้าถึงข้อมูลตามบทบาทผู้ใช้ และรองรับการยืนยันตัวตนแบบสองชั้น

### 4.1.3 Use Case ของระบบ

จากการตรวจสอบเส้นทางการทำงานในระบบ สามารถสรุป use case หลักของส่วนเว็บไซต์ได้ดังนี้

| กลุ่มผู้ใช้ | Use case หลัก |
| --- | --- |
| Guest | ค้นหาประกาศ, กรองผลลัพธ์, ดูรายละเอียดประกาศ, เปิดไฟล์ PDF |
| Registered User | เข้าสู่ระบบ, ดูแดชบอร์ดผู้ใช้, บันทึกการค้นหา, เรียกใช้ Saved Search, ดูประวัติการค้นหา, ดูประวัติการเข้าชม, ดูการแจ้งเตือน, อ่านการแจ้งเตือน, ตั้งค่าช่องทางแจ้งเตือน, จัดการโปรไฟล์, เปลี่ยนรหัสผ่าน, เปิดใช้ 2FA |
| Administrator | ดูแดชบอร์ดผู้ดูแล, จัดการประกาศ, เปลี่ยนสถานะเผยแพร่ประกาศ, จัดการผู้ใช้, เปลี่ยนสิทธิ์ผู้ใช้, ลบผู้ใช้ |

ไฟล์แผนภาพที่จัดเตรียมไว้แล้วในระบบสามารถใช้อ้างอิงประกอบรายงานได้จากโฟลเดอร์ `architecture` ได้แก่ use-case diagram, class diagram, sequence diagram และ state diagram

### 4.1.4 Use Case Text และ Use Case Scenario ที่สำคัญ

#### Use Case 1: ค้นหาประกาศจัดซื้อจัดจ้าง

- ชื่อ use case: ค้นหาประกาศจัดซื้อจัดจ้าง
- ผู้แสดงหลัก: Guest, Registered User, Administrator
- เงื่อนไขก่อนเริ่ม: ระบบมีประกาศที่เผยแพร่แล้วอย่างน้อย 1 รายการ
- เหตุการณ์หลัก:
1. ผู้ใช้เข้าสู่หน้า `procurement`
2. ผู้ใช้กรอกคำค้นหรือกำหนดตัวกรอง
3. ระบบส่งคำขอไปยังตัวควบคุมการค้นหา
4. ระบบประมวลผลเงื่อนไขผ่าน service `AnnouncementSearch`
5. ระบบแสดงรายการประกาศที่ตรงเงื่อนไข พร้อมแบ่งหน้า
6. หากเป็นผู้ใช้ที่ยืนยันอีเมลแล้ว ระบบบันทึกประวัติการค้นหา
- เงื่อนไขหลังจบ: ผู้ใช้เห็นผลการค้นหาที่กรองแล้ว และระบบอาจมีการบันทึก search history

#### Use Case 2: ดูรายละเอียดประกาศและไฟล์ PDF

- ชื่อ use case: ดูรายละเอียดประกาศ
- ผู้แสดงหลัก: Guest, Registered User, Administrator
- เงื่อนไขก่อนเริ่ม: ประกาศต้องอยู่ในสถานะ `published`
- เหตุการณ์หลัก:
1. ผู้ใช้เลือกประกาศจากหน้ารายการ
2. ระบบดึงข้อมูลประกาศและไฟล์แนบของประกาศนั้น
3. ระบบแสดงรายละเอียด เช่น ชื่อโครงการ หน่วยงาน งบประมาณ วิธีจัดซื้อจัดจ้าง วันสิ้นสุด และรายละเอียดโครงการ
4. ผู้ใช้เลือกเปิดไฟล์ PDF ของประกาศ
5. ระบบตรวจสอบว่าไฟล์เป็นของประกาศเดียวกันและมีไฟล์อยู่จริง
6. ระบบส่งไฟล์ PDF ให้ผู้ใช้ดาวน์โหลดหรือเปิดดู
7. หากเป็นผู้ใช้ที่ยืนยันอีเมลแล้ว ระบบปรับปรุงประวัติการเข้าชมประกาศ
- เงื่อนไขหลังจบ: ผู้ใช้เข้าถึงข้อมูลรายละเอียดและเอกสารประกาศได้

#### Use Case 3: บันทึกการค้นหาและรับการแจ้งเตือน

- ชื่อ use case: บันทึกการค้นหาและเปิดการแจ้งเตือน
- ผู้แสดงหลัก: Registered User
- เงื่อนไขก่อนเริ่ม: ผู้ใช้ต้องเข้าสู่ระบบและยืนยันอีเมลแล้ว
- เหตุการณ์หลัก:
1. ผู้ใช้กำหนดเงื่อนไขการค้นหา
2. ผู้ใช้บันทึกเงื่อนไขเป็น Saved Search
3. ผู้ใช้เลือกเปิด `alert_enabled`
4. เมื่อผู้ดูแลเผยแพร่ประกาศใหม่ ระบบ dispatch งาน `EvaluateSavedSearchAlerts`
5. Job เปรียบเทียบประกาศใหม่กับเกณฑ์ของ Saved Search ทั้งหมดที่เปิดแจ้งเตือน
6. หากตรงเงื่อนไข ระบบส่งการแจ้งเตือนไปยังช่องทางที่ผู้ใช้ตั้งไว้
- เงื่อนไขหลังจบ: ผู้ใช้ได้รับการแจ้งเตือนผ่านเว็บไซต์หรืออีเมลเมื่อมีประกาศใหม่ที่ตรงกับเงื่อนไข

#### Use Case 4: ผู้ดูแลระบบจัดการประกาศ

- ชื่อ use case: จัดการประกาศจัดซื้อจัดจ้าง
- ผู้แสดงหลัก: Administrator
- เงื่อนไขก่อนเริ่ม: ผู้ใช้ต้องมีบทบาทเป็น `admin`
- เหตุการณ์หลัก:
1. ผู้ดูแลเข้าสู่แดชบอร์ดผู้ดูแลระบบ
2. ผู้ดูแลเพิ่มหรือแก้ไขข้อมูลประกาศ
3. ผู้ดูแลแนบไฟล์ PDF ของประกาศ
4. ผู้ดูแลบันทึกประกาศเป็น draft หรือเผยแพร่
5. หากมีการเผยแพร่ ระบบตั้งค่า `published_at` และกระตุ้นกระบวนการตรวจจับ Saved Search ที่เกี่ยวข้อง
- เงื่อนไขหลังจบ: ข้อมูลประกาศถูกปรับปรุงในฐานข้อมูล และพร้อมให้ผู้ใช้ทั่วไปเข้าถึงเมื่อเผยแพร่แล้ว

### 4.1.5 ภาพรวมลำดับการทำงานของระบบ

ระบบมีลำดับการทำงานหลัก 4 กลุ่ม คือ

1. กลุ่มการพิสูจน์ตัวตน: ผู้ใช้ลงทะเบียน เข้าสู่ระบบ ยืนยันอีเมล รีเซ็ตรหัสผ่าน และตั้งค่า two-factor authentication ผ่าน Laravel Fortify
2. กลุ่มการค้นหา: ผู้ใช้ส่งคำค้นและตัวกรองมายัง `SearchController` จากนั้น `AnnouncementSearch` สร้าง query เพื่อดึงข้อมูลจากฐานข้อมูลแล้วส่งผลลัพธ์กลับไปยังหน้า React ผ่าน Inertia
3. กลุ่มการดูรายละเอียด: ผู้ใช้เรียกดูรายละเอียดประกาศผ่าน `ShowController` และเปิดไฟล์ผ่าน `PdfController` โดยระบบจะบันทึก listing history เมื่อผู้ใช้มีสิทธิ์ครบ
4. กลุ่มการเผยแพร่และแจ้งเตือน: ผู้ดูแลเผยแพร่ประกาศผ่าน `Admin\AnnouncementController` จากนั้นระบบส่งงานเข้าคิวให้ `EvaluateSavedSearchAlerts` ตรวจหาผู้ใช้ที่ควรได้รับการแจ้งเตือน

## 4.2 การออกแบบระบบ

### 4.2.1 สถาปัตยกรรมของระบบ

ระบบเว็บไซต์ใช้สถาปัตยกรรมแบบแยก presentation และ business logic ออกเป็น 3 ชั้นหลัก ได้แก่

1. Frontend Layer พัฒนาด้วย React และ TypeScript สำหรับแสดงผลหน้าเว็บ
2. Application Layer พัฒนาด้วย Laravel สำหรับ route, controller, request validation, job และ notification
3. Data Layer ใช้ฐานข้อมูลเชิงสัมพันธ์สำหรับเก็บข้อมูลผู้ใช้ ประกาศ ประวัติการค้นหา และข้อมูลการแจ้งเตือน

การเชื่อมต่อระหว่าง Laravel และ React ใช้ Inertia.js ทำให้ระบบสามารถส่งข้อมูลจาก controller ไปยังหน้า React ได้โดยตรงโดยไม่ต้องสร้าง REST API แยกสำหรับทุกหน้า ในเชิงปฏิบัติ โครงสร้างนี้ช่วยลดความซ้ำซ้อนของการจัดการ route, auth, validation และ shared props

### 4.2.2 Package Diagram และ Component Diagram เชิงตรรกะ

สามารถสรุป package และ component หลักของระบบเว็บไซต์ได้ดังนี้

| Package/Component | หน้าที่หลัก |
| --- | --- |
| Authentication | ลงทะเบียน, เข้าสู่ระบบ, ยืนยันอีเมล, รีเซ็ตรหัสผ่าน, 2FA |
| Procurement | ค้นหาประกาศ, แสดงรายละเอียดประกาศ, เปิดไฟล์ PDF |
| User Features | แดชบอร์ดผู้ใช้, Saved Search, Search History, Listing History, Notifications |
| Admin | แดชบอร์ดผู้ดูแล, จัดการประกาศ, จัดการผู้ใช้ |
| Settings | โปรไฟล์, รหัสผ่าน, appearance, two-factor settings |
| Shared UI | layout, navigation, ตารางข้อมูล, pagination, form components |

ความสัมพันธ์ของคอมโพเนนต์สามารถอธิบายได้ดังนี้

1. Route ส่งคำขอเข้าสู่ Controller
2. Controller ประมวลผลและเรียกใช้ Model, Service หรือ Job ตามกรณี
3. Controller ส่งผลลัพธ์กลับเป็น Inertia page หรือ JSON response
4. React page และ shared components ทำหน้าที่แสดงผลและรับข้อมูลจากผู้ใช้

| `User` | เก็บข้อมูลผู้ใช้ บทบาท และความสัมพันธ์กับ Saved Search และ Notification Preference |
| `Announcement` | เก็บข้อมูลประกาศจัดซื้อจัดจ้าง เช่น ชื่อ หน่วยงาน งบประมาณ สถานะ และวันสิ้นสุด |
| `AnnouncementAttachment` | เก็บข้อมูลไฟล์แนบ PDF ของประกาศ |
| `SavedSearch` | เก็บชื่อชุดการค้นหา เงื่อนไขแบบ JSON และสถานะการเปิดแจ้งเตือน |
| `SearchHistory` | เก็บประวัติการค้นหา ผลลัพธ์ที่พบ และเวลาที่ค้นหา |
| `ListingHistory` | เก็บประวัติการดูประกาศหรือดาวน์โหลดเอกสารของผู้ใช้ |
| `NotificationPreference` | เก็บการตั้งค่าช่องทางแจ้งเตือนผ่านเว็บไซต์และอีเมล |
| `AnnouncementSearch` | Service สำหรับสร้าง query การค้นหาจากชุดเกณฑ์เดียวกัน |
| `EvaluateSavedSearchAlerts` | Job สำหรับประเมิน Saved Search กับประกาศใหม่ |
| `NewMatchingAnnouncement` | Notification สำหรับแจ้งผู้ใช้เมื่อมีประกาศใหม่ตรงเงื่อนไข |

แนวคิดเชิงวัตถุที่ใช้จริงในระบบคือการแยก business rule ที่ใช้ซ้ำออกจาก controller เช่น การค้นหาประกาศถูกย้ายไปอยู่ใน `AnnouncementSearch` เพื่อให้ logic ชุดเดียวกันถูกนำไปใช้ทั้งในหน้า search และ background job ของการแจ้งเตือน

### 4.2.4 การออกแบบฐานข้อมูลเชิงสัมพันธ์

ตารางหลักของระบบเว็บไซต์มีดังนี้

| ตาราง | รายละเอียดข้อมูลสำคัญ |
| --- | --- |
| `users` | เก็บชื่อ อีเมล รหัสผ่าน บทบาท การยืนยันอีเมล และข้อมูล 2FA |
| `announcements` | เก็บข้อมูลประกาศ เช่น title, organization, category, method, budget, status, publication_status, deadline |
| `announcement_attachments` | เก็บชื่อไฟล์จริง ชื่อไฟล์แสดงผล และความสัมพันธ์กับประกาศ |
| `saved_searches` | เก็บชื่อการค้นหา เงื่อนไขแบบ JSON สถานะเปิดแจ้งเตือน และเวลาแจ้งเตือนล่าสุด |
| `search_history` | เก็บเกณฑ์ที่ใช้ค้นหา จำนวนผลลัพธ์ และเวลาค้นหา |
| `listing_history` | เก็บว่าใครดูประกาศใดและดูเมื่อใด |
| `notification_preferences` | เก็บการตั้งค่า website notification และ email notification |
| `notifications` | เก็บข้อความแจ้งเตือนของ Laravel notification channel แบบฐานข้อมูล |

ความสัมพันธ์ระหว่างตารางสามารถอธิบายได้ดังนี้

1. ผู้ใช้ 1 คน มี Saved Search ได้หลายรายการ
2. ผู้ใช้ 1 คน มี Notification Preference ได้ 1 รายการ
3. ผู้ใช้ 1 คน มี Search History ได้หลายรายการ
4. ผู้ใช้ 1 คน มี Listing History ได้หลายรายการ
5. ประกาศ 1 รายการ มีไฟล์แนบได้หลายรายการ
6. ประกาศ 1 รายการ สามารถถูกอ้างถึงใน Listing History และ Notification ได้หลายครั้ง

ในเชิง E-R diagram หากต้องการนำไปใส่รายงานฉบับเต็มสามารถวาดจากตารางและความสัมพันธ์ข้างต้นได้โดยตรง เนื่องจากโครงสร้าง foreign key ของระบบถูกกำหนดไว้ชัดเจนใน migration แล้ว

### 4.2.5 การออกแบบส่วนติดต่อผู้ใช้

หน้าจอหลักของระบบเว็บไซต์ประกอบด้วย

1. หน้า Search ประกาศจัดซื้อจัดจ้าง: แสดงช่องค้นหา ตัวกรอง งบประมาณแบบ slider ตัวเลือกเรียงลำดับ รายการประกาศ และ pagination
2. หน้า Announcement Detail: แสดงข้อมูลประกาศทั้งหมด พร้อมตัวแสดงสถานะและตัวดูเอกสาร PDF
3. หน้า User Dashboard: แสดงสถิติการใช้งานล่าสุด รายการค้นหาที่บันทึกไว้ และประวัติการดูประกาศล่าสุด
4. หน้า Saved Searches: ใช้จัดการชุดเงื่อนไขที่ผู้ใช้บันทึกไว้ และเรียกใช้งานซ้ำได้
5. หน้า History: แยกประวัติการดูประกาศและประวัติการค้นหาออกจากกันแบบแบ่งหน้า
6. หน้า Notifications: แสดงรายการแจ้งเตือนและสถานะการอ่าน พร้อมค่า preference ของการแจ้งเตือน
7. หน้า Admin Dashboard: แสดงตัวเลขสรุปและรายการประกาศสำหรับจัดการ
8. หน้า Admin Users: แสดงรายการผู้ใช้เพื่อเปลี่ยนสิทธิ์และลบผู้ใช้
9. หน้า Settings: ใช้แก้ไขโปรไฟล์ รหัสผ่าน รูปแบบการแสดงผล และ two-factor authentication

การออกแบบหน้าจอใช้ shared layout ร่วมกันผ่าน `AppHeaderLayout` และใช้ชุด UI component กลาง เช่น Button, Card, Input, Select, Pagination, Badge, DataTable และ Dialog เพื่อให้หน้าจอมีรูปแบบที่สม่ำเสมอ

### 4.3.3 ข้อกำหนดเฉพาะของแต่ละส่วนงาน

#### 1) โมดูลค้นหาประกาศ

- รับ parameter จาก query string เช่น `query`, `organization`, `method`, `category`, `budget_min`, `budget_max`, `sort`
- ใช้ service `AnnouncementSearch` เป็นตัวสร้างเงื่อนไข query
- จำกัดการแสดงผลเฉพาะประกาศที่อยู่ในสถานะ `published`
- รองรับการแบ่งหน้าและเก็บ query string เดิมไว้เมื่อเปลี่ยนหน้า

#### 2) โมดูลรายละเอียดประกาศ

- ต้องเปิดได้เฉพาะประกาศที่เผยแพร่แล้ว
- ต้องโหลดไฟล์แนบที่สัมพันธ์กับประกาศเท่านั้น
- ต้องรองรับการเปิดไฟล์ PDF แบบ stream download
- ต้องบันทึกประวัติการเข้าชมสำหรับผู้ใช้ที่ยืนยันอีเมลแล้ว

#### 3) โมดูลผู้ใช้ทั่วไป

- หน้า dashboard แสดงข้อมูลสรุปจากฐานข้อมูลจริง เช่น จำนวน Saved Search และประวัติการดูล่าสุด
- หน้า saved searches ต้องให้สร้าง แก้ไข ลบ และเรียกใช้งานรายการค้นหาที่บันทึกไว้ได้
- หน้า history ต้องแสดงทั้ง search history และ listing history แบบแยกชุดข้อมูล
- หน้า notifications ต้องแสดงการแจ้งเตือนล่าสุด ตั้งค่าช่องทางรับแจ้งเตือน และทำเครื่องหมายว่าอ่านแล้วได้

#### 4) โมดูลผู้ดูแลระบบ

- หน้า admin dashboard แสดงสถิติของประกาศและจำนวนผู้ใช้
- โมดูลจัดการประกาศรองรับ create, update, delete, publish, hide และแนบไฟล์ PDF
- โมดูลจัดการผู้ใช้รองรับเปลี่ยน role และลบผู้ใช้
- ต้องมี guard ป้องกันการลดสิทธิ์หรือลบผู้ดูแลระบบคนสุดท้าย

#### 5) โมดูลสิทธิ์และความปลอดภัย

- route ระดับ admin ต้องผ่าน middleware `auth`, `verified` และ `role:admin`
- route ระดับผู้ใช้ต้องผ่าน `auth` และ `verified`
- route `dashboard` ต้อง redirect ไปยังหน้าที่เหมาะสมตามบทบาท
- มีการกำหนด two-factor authentication, email verification และ password reset ผ่าน Fortify

### 4.3.4 การติดต่อกับฐานข้อมูลและ service class

การเชื่อมต่อข้อมูลของระบบเว็บไซต์อาศัย Eloquent ORM ของ Laravel โดย controller แต่ละตัวเรียกใช้งาน model และ relation ตามหน้าที่ เช่น

1. `SearchController` ใช้ `AnnouncementSearch` เพื่อสร้าง query จากเงื่อนไขค้นหา
2. `ShowController` และ `PdfController` ใช้ `Announcement` และ `AnnouncementAttachment` เพื่อดึงรายละเอียดประกาศและเอกสารแนบ
3. `SavedSearchController` ใช้ `SavedSearch` สำหรับจัดการชุดการค้นหาของผู้ใช้
4. `HistoryController` ใช้ `SearchHistory` และ `ListingHistory` เพื่อสรุปประวัติการใช้งาน
5. `NotificationController` และ `NotificationPreferenceController` ใช้ Laravel notification และ `NotificationPreference` เพื่อควบคุมช่องทางการแจ้งเตือน
6. `Admin\AnnouncementController` ใช้ model ประกาศร่วมกับ queue job `EvaluateSavedSearchAlerts` เพื่อกระตุ้นการแจ้งเตือนเมื่อมีประกาศใหม่

แนวทางดังกล่าวทำให้ controller มีหน้าที่ประสานงานเป็นหลัก และย้าย logic ที่ใช้ร่วมกันไปไว้ใน service หรือ job ที่เหมาะสม

### 4.3.5 คอมโพเนนต์ที่นำมาใช้ในระบบ

คอมโพเนนต์สำคัญที่นำมาใช้ในหน้าเว็บ ได้แก่

1. `Input`, `Checkbox`, `Select`, `Slider` สำหรับการป้อนค่าค้นหาและกรองข้อมูล
2. `Card`, `Badge`, `StatusBadge` สำหรับการแสดงสถานะและสรุปข้อมูล
3. `Pagination` สำหรับการแบ่งหน้ารายการข้อมูล
4. `Dialog` สำหรับฟอร์มเพิ่มและแก้ไขข้อมูลในฝั่งผู้ดูแลระบบ
5. `DataTable` สำหรับแสดงตารางข้อมูลในหน้า admin
6. `Timeline` สำหรับแสดงลำดับเหตุการณ์ของประกาศหรือกิจกรรมผู้ใช้

### 4.3.6 การใช้งานระบบเบื้องต้น

ลำดับการใช้งานระบบในส่วนเว็บไซต์สามารถสรุปได้ดังนี้

1. ผู้ใช้ทั่วไปเข้าหน้าแรกหรือหน้า `procurement` เพื่อค้นหาประกาศ
2. ผู้ใช้เลือกดูรายละเอียดของประกาศและเปิดเอกสาร PDF ที่แนบไว้
3. ผู้ใช้ที่ต้องการฟังก์ชันเพิ่ม เช่น Saved Search หรือประวัติการใช้งาน ต้องสมัครสมาชิก ยืนยันอีเมล และเข้าสู่ระบบ
4. ผู้ใช้ที่เข้าสู่ระบบสามารถเข้าหน้าแดชบอร์ด จัดการ Saved Search ดูประวัติ และตั้งค่าการแจ้งเตือน
5. ผู้ดูแลระบบเข้าสู่หน้า `admin` เพื่อจัดการประกาศและผู้ใช้งาน

## 4.4 การทดสอบระบบ

### 4.4.1 แนวทางการทดสอบ

ระบบเว็บไซต์ใช้การทดสอบ 2 ระดับหลัก ได้แก่

1. Feature Test ด้วย Pest/Laravel สำหรับตรวจสอบ route, authorization, model behavior และการทำงานของ controller
2. Browser Test ด้วย Playwright สำหรับจำลองการใช้งานจริงบนเบราว์เซอร์ เช่น guest flow, auth flow, redirect และ admin flow

แนวทางนี้ช่วยให้ครอบคลุมทั้งการทดสอบตรรกะภายในและการทดสอบพฤติกรรมจากมุมมองผู้ใช้งานจริง

### 4.4.2 ตัวอย่างหัวข้อทดสอบที่มีในระบบ

| หมวดทดสอบ | ตัวอย่างสิ่งที่ตรวจสอบ |
| --- | --- |

| Dashboard Redirect | `dashboard` redirect ไปหน้า admin หรือ user ตามบทบาท |
| Procurement | ค้นหาประกาศได้, ดูรายละเอียดประกาศได้, เปิด PDF ได้ |

| Admin | seed ผู้ดูแลเริ่มต้น, promote user เป็น admin, ป้องกันการลบ admin คนสุดท้าย |
| Browser E2E | guest search flow, redirect behavior, auth flow, admin flow |

4. เลือกเปิดหน้ารายละเอียดประกาศ
5. ตรวจสอบว่าหน้ารายละเอียดและข้อมูลหลักแสดงถูกต้อง
- ผลที่คาดหวัง: ผู้ใช้เข้าถึงหน้ารายละเอียดได้และไม่เห็นเมนูสำหรับฟังก์ชันเฉพาะสมาชิก

#### กรณีทดสอบที่ 2: ผู้ใช้ทั่วไปไม่สามารถเข้าหน้า admin

- วัตถุประสงค์: ตรวจสอบการบังคับสิทธิ์จากฝั่งเซิร์ฟเวอร์
- ขั้นตอนทดสอบ:
1. สร้างผู้ใช้บทบาท `registered`
2. เข้าสู่ระบบด้วยผู้ใช้นั้น
3. เรียกหน้า `admin`
- ผลที่คาดหวัง: ระบบตอบกลับสถานะ `403 Forbidden`

#### กรณีทดสอบที่ 3: ผู้ดูแลระบบเผยแพร่ประกาศและกระตุ้นงานแจ้งเตือน

- วัตถุประสงค์: ตรวจสอบการเชื่อมกันระหว่างโมดูลจัดการประกาศและระบบแจ้งเตือน
- ขั้นตอนทดสอบ:
1. สร้าง Saved Search ที่เปิดแจ้งเตือน
2. สร้างประกาศใหม่ที่ตรงเงื่อนไข
3. เปลี่ยนสถานะประกาศเป็น `published`
4. ตรวจสอบว่าระบบ dispatch job สำหรับประเมินการแจ้งเตือน
- ผลที่คาดหวัง: Saved Search ที่ตรงเงื่อนไขได้รับ notification ตาม preference ที่กำหนด

#### กรณีทดสอบที่ 4: ป้องกันการลดสิทธิ์ผู้ดูแลระบบคนสุดท้าย

- วัตถุประสงค์: ป้องกันความเสี่ยงที่ระบบจะไม่มีผู้ดูแลเหลืออยู่
- ขั้นตอนทดสอบ:
1. สร้างผู้ใช้ admin เพียง 1 คน
2. เรียก API เปลี่ยนบทบาทของผู้ใช้นั้นเป็น `registered`
- ผลที่คาดหวัง: ระบบตอบกลับสถานะ `422` และไม่เปลี่ยนบทบาทของผู้ใช้

### 4.4.4 สรุปผลการทดสอบที่เหมาะสมต่อการรายงาน

จากโครงสร้าง test suite ที่มีอยู่ ระบบสามารถสรุปผลเชิงคุณภาพได้ว่า

1. ส่วนการควบคุมสิทธิ์ถูกทดสอบทั้งในระดับ route และในระดับ browser flow
2. ส่วนการพิสูจน์ตัวตนและการตั้งค่าความปลอดภัยมีชุดทดสอบรองรับหลายกรณี เช่น การยืนยันอีเมลและ two-factor authentication
3. ส่วนการค้นหาประกาศและการเปิดดูรายละเอียดมีชุดทดสอบเฉพาะทางรองรับ
4. ส่วนงานผู้ดูแลระบบมีการทดสอบทั้งการ bootstrap ผู้ดูแลเริ่มต้นและเงื่อนไข last admin safeguard

ดังนั้นระบบเว็บไซต์ส่วนที่พัฒนาในรีโปนี้มีความพร้อมในระดับหนึ่งทั้งด้านการใช้งานจริงและด้านการตรวจสอบความถูกต้องอัตโนมัติ อย่างไรก็ตาม หากนำไปใช้ในรายงานฉบับสมบูรณ์ ควรแนบภาพหน้าจอของแต่ละหน้าและผลการรันทดสอบเพิ่มเติมเพื่อใช้เป็นหลักฐานเชิงประจักษ์

## สรุปท้ายบท

บทที่ 4 นี้แสดงให้เห็นว่าระบบเว็บไซต์ของโครงการถูกพัฒนาในลักษณะที่สอดคล้องกันตั้งแต่การวิเคราะห์ผู้ใช้และความต้องการ การออกแบบสถาปัตยกรรมและฐานข้อมูล การลงมือพัฒนาด้วย Laravel, Inertia และ React ไปจนถึงการทดสอบด้วย Pest และ Playwright โดยส่วนเว็บไซต์ที่ทำเสร็จแล้วครอบคลุมงานหลักของการค้นหาประกาศ การดูรายละเอียดเอกสาร การใช้งานของสมาชิก และการจัดการข้อมูลโดยผู้ดูแลระบบ ส่วนงาน OCR ยังไม่ถูกนำมารวมในขอบเขตของบทนี้ตามข้อกำหนด
